# 第 1 章：源图像素预检——图片文件不大，为什么处理时内存会涨？

本章从你已经读过的 `Resize` 出发，只完成一件事：**在完整解码之前，检查原图的宽高和像素数量，拒绝超过预算的图片。** 我们先沿着一次现有请求走完流程，再解释问题为什么发生，最后把检查逐步接进去。

这里依据的是 2026-10-13 的实际源码，项目仍是标准库 `net/http` 同步服务。文中的新增代码是供你亲手实现和对照的参考；正式项目还没有接入源图预检。本章的示例在独立副本中验证，不需要启动 Docker。

学习时先读到第 8 节，写出自己的第一版，再展开第 9 节的参考代码。之后用第 10 节的例子检查结果。每次只推进这一章，下一章等当前内容读顺、练习跑通后再写。

## 1. 先拿一张图片，走一遍当前请求

假设你上传一张 `4000×3000` 的 PNG，要求把宽度缩到 `800`。为了讨论方便，先假设这个 PNG 文件压缩后小于 10 MiB；它最终到底多少字节，要以实际编码结果为准。

你可以把当前请求的路径读成下面这一条线：

```text
浏览器上传 file 和 width=800
→ Handler 限制整个请求体，解析 multipart
→ 取出文件，检查声明的 Content-Type 和目标宽度
→ 建立处理 context，调用 Service.Resize
→ 等待计算名额
→ 把文件读成 imgData，并检查文件字节上限
→ image.Decode，把压缩图片展开为可以访问像素的图像
→ Bounds，取得原图宽高
→ 算目标高度，申请目标图
→ 缩放、编码，返回图片字节
→ Handler 写 HTTP 响应
```

这条线上有几个名字需要重新对应到实际文件，否则一会儿讨论“在前面检查”时，很容易不知道到底是哪个前面。

| 源码文件 | 当前负责的事情 |
|---|---|
| [cmd/server/main.go](D:/GO/image-processor/cmd/server/main.go) | 加载配置，创建 Stats 和 Router，启动 HTTP 服务 |
| [internal/server/http.go](D:/GO/image-processor/internal/server/http.go) | 创建共享 Service，把 `/resize` 路由绑定到 Handler |
| [internal/process/handler.go](D:/GO/image-processor/internal/process/handler.go) | 处理 HTTP 表单、参数与响应，把 Service 的错误翻译成状态码 |
| [internal/process/service.go](D:/GO/image-processor/internal/process/service.go) | 读文件、解码、缩放和编码，控制图片处理的并发名额 |
| [internal/config/config.go](D:/GO/image-processor/internal/config/config.go) | 把 YAML 内容转换成 Go 配置，并检查配置是否合法 |

Handler 当前先检查整个请求体。默认的请求体上限是 11 MiB，里面除了图片，还包括 multipart 边界和表单字段。进入 Service 后，单独读取图片文件时又检查 10 MiB 上限。所以“请求体大小”和“图片文件大小”是两道不同的检查。

进入 `Resize` 时，`file` 是一个 `io.Reader`。你可以通过它连续读取文件字节，但此时还没有得到一张能访问像素的图片。读完之后的 `imgData []byte` 仍然是 PNG 或 JPEG 的编码数据，里面保存的是文件格式规定的字节。

随后代码执行：

```go
img, _, err := image.Decode(bytes.NewReader(imgData))
```

这一行才开始完整解码。成功返回的 `img` 实现 `image.Image` 接口，缩放算法可以通过它获取像素。接下来取得 `Bounds` 时，大量解码工作已经发生。因此，**在 `Bounds` 后面才检查原图是不是太大，无法阻止之前的完整解码开销。**

对于这张 `4000×3000` 的图片，当前代码算出的目标高度是：

```text
目标高度 = 800 × 3000 ÷ 4000 = 600
```

目标图随后被创建为 `800×600` 的 RGBA。缩放算法把原图的像素转换到目标图，再编码成响应文件。这说明，即使最终只要一张小图，当前算法也要先取得完整原图。

## 2. 为什么“文件只有几 MiB”说明不了解码内存

文件大小描述的是编码数据有多少字节，而图片尺寸描述的是展开后有多少个像素。同一尺寸的图片，内容越容易压缩，文件就可能越小；一张大面积纯色的 PNG，与同尺寸、包含大量细碎变化的 PNG，可以有不同的文件大小。

因此，一张上传时很小的图，仍然可能有很多像素。为了看清数量级，我们先按 RGBA 的像素存储来估算。RGBA 通常用 R、G、B、A 四个 8 位分量保存一个像素，像素数组大约需要：

```text
宽 × 高 × 4 字节
```

对 `4000×3000` 来说：

```text
像素数量 = 4000 × 3000 = 12,000,000
RGBA 像素字节 = 12,000,000 × 4 = 48,000,000
换成 MiB = 48,000,000 ÷ 1,048,576 ≈ 45.8 MiB
```

这是像素数组的估算，尚未包括输入文件、解码器内部数据、目标图、编码输出和运行时开销。JPEG 解码可能得到 YCbCr，PNG 也可能得到其他像素表示，不能把每一张实际原图都认定为“恰好每像素 4 字节”。不过，你当前明确创建的目标图是 `image.NewRGBA`，其像素数组确实采用四分量存储。这里的 4 字节用于说明资源数量级，而不是宣称测得了某张图片的实际堆内存。[Go RGBA 文档](https://pkg.go.dev/image#RGBA)

如果原图改为 `10000×10000`，按 RGBA 估算就要约 381.5 MiB。假设同时有四张这样的图展开，仅这四份像素数组就约为 1.49 GiB。你当前的 `max_concurrent: 4` 限制了处理数量，却没有限制每一份处理有多大。

所以，文件字节上限解决“读入多少压缩数据”，源像素预算解决“允许展开多大的原图”。我们需要让两道检查同时存在。以后还要补目标图和等待请求的限制，但本章先把源图这一处补好。

## 3. 我们究竟想新增什么行为

动手前先固定规则。本章把源图预算暂定为 **20,000,000 个像素**。它是当前练习的配置起点，需要在后续完整负载实验中结合内存和并发调整，并不是适用于所有部署环境的固定答案。

| 输入 | 像素数量或检查情况 | 本章预期行为 |
|---|---:|---|
| `4000×3000` | 12,000,000 | 允许继续解码 |
| `5000×4000` | 20,000,000 | 恰好达到上限，允许 |
| `5001×4000` | 20,004,000 | 拒绝，返回源像素超限错误 |
| `6000×4000` | 24,000,000 | 拒绝，返回源像素超限错误 |
| 无法识别的图片内容 | 获取配置失败 | 沿用解码错误 |
| 头部可识别，后面的图像数据损坏 | 预检可能成功 | 后续完整解码仍应拒绝 |
| 源像素配置为 0 或负数 | 服务配置非法 | 启动时拒绝配置 |

“允许”只意味着通过源图预算这一关。图片随后仍可能因为内容损坏、处理取消或其他错误而失败，不能把预检成功当成处理成功。

HTTP 层也要表达新行为。源像素超预算时，本章约定返回 `413`，响应为：

```json
{"error":"source image pixel limit exceeded"}
```

这个 413 表示输入超过服务允许的资源预算，既可能来自文件字节，也可能来自源像素。二者通过不同错误和消息区分。图片无法解码时仍使用已有的 `422`，配置非法则应在启动阶段发现，不能把错误配置归咎于上传用户。

## 4. 为什么检查要放在 Service，而且放在这个位置

如果只在 Handler 里检查，当前 HTTP 请求当然可以受到保护。但是以后可能有后台 worker 直接调用 `Resize`，或者测试直接调用 Service。如果它们绕过 Handler，原图就又会未经预算检查进入解码。

源像素限制属于图片处理本身的约束，因此应该由 Service 守住。HTTP 层负责把错误翻译成 413；Service 负责判断这张图能不能进入完整解码。这样，处理逻辑与网络协议各自有明确职责。

在当前 Service 内，最适合插入检查的位置是两种读取分支汇合之后：

```text
取得计算名额
→ 池化读取 / 普通读取
→ 得到同一个 imgData
→ 新增：获取源配置，检查宽高和像素预算
→ 通过后才完整 Decode
→ 原有缩放与编码
```

这样做有一个直接好处：不用在“池开”和“池关”两条分支里各写一遍像素检查。两条分支都已经完成字节上限校验，最后都交出 `imgData`，后续可以共用同一个预检函数。

预检失败后会 `return`。之前登记的 `defer` 仍会执行，因此计算名额会释放；如果借用了输入缓冲区，也会归还。新增代码不需要另写一套手动释放逻辑，但测试需要确认失败后下一次请求还能取得名额。

这个检查发生时，压缩文件已经读入内存，计算名额也已经取得。它保护的是后续的完整解码，不负责减少本次文件读取，也不解决 Handler 在取得 Service 名额前就解析 multipart 的问题。知道这道检查覆盖哪里，才能判断是否还需要下一道保护。

## 5. DecodeConfig 与 Decode 分别给你什么

`image.DecodeConfig` 提供图片配置，主要是宽、高和颜色模型，并返回识别出的格式名。它让我们在完整解码前获得做预算判断所需的信息。`image.Decode` 则生成完整的图像对象，供后续访问像素和缩放。[Go 图片配置接口](https://pkg.go.dev/image#DecodeConfig)

调用形式是：

```go
cfg, actualFormat, err := image.DecodeConfig(bytes.NewReader(imgData))
```

`cfg.Width`、`cfg.Height` 是这里需要的源尺寸。`actualFormat` 可能是 `"png"` 或 `"jpeg"`，来自实际编码内容，而不是上传者填写的 Content-Type。`err` 表示当前是否能识别配置。

此处要分清它与现有 Handler 的关系。Handler 当前依据上传声明选择输出格式；本章先取出实际源配置并检查像素，**声明与真实格式是否必须一致、能否转换输出格式，将在下一章单独定义。**不要在加像素限制时顺手改变另一套接口规则。

预检也不是对整张图的完整验证。以 PNG 为例，尺寸信息可以先被读出来，但后续像素数据仍可能缺失。遇到这种输入，允许先通过尺寸检查，随后由完整 Decode 返回错误。这里没有固定“只读 24 字节”这样的通用长度；不同格式取得配置所需的读取量由解码器决定。

还有一个容易忽略的点：Go 的 `image` 包需要对应格式的解码器注册。你当前 Service 已经导入 `image/jpeg` 和 `image/png`，编码器包的初始化也会完成注册。后面独立的预检示例会使用空白导入 `_ "image/jpeg"`、`_ "image/png"`，让示例自身明确包含这两种解码器。

## 6. 为什么预检以后要再建一个 Reader

Reader 读取数据时会推进位置。假设把同一个 Reader 先交给 DecodeConfig，再交给 Decode：

```go
reader := bytes.NewReader(imgData)
cfg, _, err := image.DecodeConfig(reader)
if err != nil {
    return nil, err
}

// reader 已经被读取过。下面并不是从文件开头重新读取。
img, _, err := image.Decode(reader)
```

问题在于，Decode 通常需要从图片开头识别格式。它拿到的 Reader 此时已经不在开头，可能返回“unknown format”之类的错误。部分解码器还会通过缓冲读取提前消费一些字节，所以你不应该猜测当前位置，再随意减去一个固定长度。

当前项目已经有完整的 `imgData`，因此可以采用很直接的做法：

```go
cfg, _, err := image.DecodeConfig(bytes.NewReader(imgData))
if err != nil {
    return nil, err
}

// 宽高检查通过后，新建一个从位置 0 开始的 Reader。
img, _, err := image.Decode(bytes.NewReader(imgData))
```

两个 Reader 各自保存读取位置，但都引用同一份字节切片。新建 Reader 不会把整个 PNG 文件又复制一遍。你可以理解成“同一本书，两张分别从第一页开始的书签”，书的内容仍是一份。[Go bytes.NewReader 文档](https://pkg.go.dev/bytes#NewReader)

也可以在支持 Seek 的 Reader 上主动回到开头，但这里没有必要给处理流程增加对 Seek 的要求。原始参数是普通 `io.Reader`，它本来就不保证可以倒退；而 `imgData` 已经足够支持从头重读。

## 7. 检查像素时，为什么不直接写宽乘高

第一版最自然的写法是：

```go
if cfg.Width * cfg.Height > maxPixels {
    // 拒绝
}
```

这里既有类型问题，也有计算问题。`Width` 和 `Height` 是 `int`，而我们的预算准备使用 `int64`；即使解决类型不一致，乘法也可能先在 `int` 范围内溢出。

下面这种写法并没有修复“先溢出”的问题：

```go
pixels := int64(cfg.Width * cfg.Height)
```

它先算两个 int 的乘积，再转换结果。假如运行在 32 位环境，`65536×65536` 已经超出 int 范围，转换成 int64 时得到的是溢出后的值。你的当前电脑是 64 位，但代码审查时不能把运行环境当成宽高计算的正确性证明。

即便改成 `int64(width) * int64(height)`，从通用整数计算角度仍需要考虑乘积边界。我们可以利用正整数的不等式，避免先生成乘积：

```text
width × height > budget
等价于
width > floor(budget ÷ height)
```

于是检查写成：

```go
if cfg.Width <= 0 || cfg.Height <= 0 {
    // 非法尺寸，不能继续；也避免后面除以 0。
}

if int64(cfg.Width) > maxPixels/int64(cfg.Height) {
    // 源像素超预算。
}
```

看一个恰好达到上限的例子。预算为 `20,000,000`，高度为 `4000`，除法结果就是 `5000`。宽度 `5000` 没有“大于”这个值，允许；宽度 `5001` 大于它，拒绝。这也解释了为什么我们使用 `>`，而不是 `>=`。

预算必须先保证为正数。配置加载负责在启动前拒绝 0 或负数；独立函数也会检查这个参数，避免直接调用时出现模糊行为。这是“配置入口校验”和“函数自身契约”各自发挥作用。

## 8. 你先写第一版，按四个小步骤推进

先不要同时改五个文件。第一步只新增一个独立预检函数，让它接收 `imgData` 和像素预算，返回图片配置、实际格式或错误。这样你可以先确认自己知道如何读配置、如何算边界，不受 HTTP 和配置传递影响。

第二步，把它插到现有 Service 的读取分支之后、Decode 之前。为了先看见行为，可以临时传入常量 `20_000_000`。此时先跑普通图片与超预算场景，确认原有缩放仍成功，预检失败不会漏掉名额释放。

第三步，确认核心行为后，再把常量接成 `process.max_source_pixels`。你要沿着 YAML → rawConfig → ProcessConfig → Router → Service 走一次，说明预算在哪一步从配置文件变成 Service 的字段。不要只在 YAML 增加一行却从未读取它。

第四步，最后接 HTTP 错误映射并补验证。Service 返回源像素超限错误，Handler 转为 413；原有坏图片仍然 422。运行所有原有测试，确认这次改动没有改变请求体上限等已有行为。

## 9. 完整核心参考与逐处接入

### 9.1 新增独立预检函数

下面是建议新增的 `internal/process/preflight.go` 全文。`ErrDecode` 使用现有 Service 中已经定义的错误，不能再重复定义同名变量。

<details>
<summary>完成自己的第一版后，展开预检函数参考</summary>

```go
package process

import (
    "bytes"
    "errors"
    "fmt"
    "image"
    _ "image/jpeg"
    _ "image/png"
)

var ErrSourcePixels = errors.New("source image pixel limit exceeded")

func InspectSource(data []byte, maxPixels int64) (image.Config, string, error) {
    if maxPixels <= 0 {
        return image.Config{}, "", fmt.Errorf("max source pixels must be > 0")
    }

    cfg, format, err := image.DecodeConfig(bytes.NewReader(data))
    if err != nil {
        return image.Config{}, "", fmt.Errorf("%w: %w", ErrDecode, err)
    }

    if cfg.Width <= 0 || cfg.Height <= 0 {
        return image.Config{}, "", fmt.Errorf(
            "%w: invalid source dimensions %dx%d",
            ErrDecode, cfg.Width, cfg.Height,
        )
    }

    if int64(cfg.Width) > maxPixels/int64(cfg.Height) {
        return image.Config{}, "", fmt.Errorf(
            "%w: dimensions=%dx%d, limit=%d",
            ErrSourcePixels, cfg.Width, cfg.Height, maxPixels,
        )
    }

    return cfg, format, nil
}
```

</details>

函数先处理错误配置，再取得配置，随后检查正尺寸和像素预算。超过预算时用 `%w` 包裹 `ErrSourcePixels`，并附上尺寸信息。这样，日志或测试能看到具体尺寸，HTTP 层也能用 `errors.Is` 稳定识别错误，不需要比较整段错误字符串。

例如，返回错误可能包含 `dimensions=5001x4000, limit=20000000`。这段文字会随着输入变化，而错误类别仍是 `ErrSourcePixels`。HTTP 响应可以保持稳定的英文消息，不必把内部全部错误细节原样发给客户端。

### 9.2 在 Service 中接入，保留两种读取方式

第一轮练习时，在 `if s.poolEnabled { ... } else { ... }` 整个分支结束之后，原有 Decode 之前加入：

```go
sourceCfg, _, err := InspectSource(imgData, 20_000_000)
if err != nil {
    return nil, err
}
```

这里的下划线暂时忽略实际格式。源尺寸会在后面参与一致性检查。随后保留原有的完整解码，但仍使用新的 Reader：

```go
img, _, err := image.Decode(bytes.NewReader(imgData))
if err != nil {
    return nil, fmt.Errorf("%w: %w", ErrDecode, err)
}

bounds := img.Bounds()
srcW := bounds.Dx()
srcH := bounds.Dy()
if srcW <= 0 || srcH <= 0 {
    return nil, fmt.Errorf("invalid image dimensions: %dx%d", srcW, srcH)
}

if srcW != sourceCfg.Width || srcH != sourceCfg.Height {
    return nil, fmt.Errorf("%w: source dimensions changed after decode", ErrDecode)
}
```

一致性检查不能替代解码前的预算检查，因为它发生在完整解码之后。它负责确认后续真正使用的图像尺寸与预检结果一致。接下来的 `newH`、目标图、Scale 和 Encode 暂时保持原有行为。

注意 `:=` 的作用域。预检这一行声明了 `sourceCfg` 和 `err`；后面的 `img, _, err := ...` 仍然合法，因为同一作用域中有新变量 `img`，而已有的 `err` 被重新赋值。

### 9.3 核心跑通后，再接配置

在 `configs/config.yaml` 的现有 process 节点中增加一项，保留其他配置：

```yaml
process:
  timeout: "15s"
  max_concurrent: 4
  max_file_size: 10485760
  max_request_size: 11534336
  max_source_pixels: 20000000
```

`internal/config/config.go` 有两套结构。`rawConfig.Process` 接收 YAML，所以新增字段需要 tag：

```go
MaxSourcePixels int64 `yaml:"max_source_pixels"`
```

而供程序使用的 `ProcessConfig` 增加对应字段：

```go
MaxSourcePixels int64
```

在 `convert` 创建 `ProcessConfig` 的地方，再加入这一行赋值：

```go
MaxSourcePixels: raw.Process.MaxSourcePixels,
```

最后，在 `validate` 中加入：

```go
if cfg.Process.MaxSourcePixels <= 0 {
    return fmt.Errorf("process.max_source_pixels must be > 0")
}
```

四处分别承担接收、保存、转换和校验。如果少了转换，YAML 虽然读到了值，Service 仍拿不到；如果少了校验，缺失字段会变成零值，直到处理请求时才暴露问题。

### 9.4 把配置传给 Service

Service 新增 `maxSourcePixels int64` 字段。接配置时，把构造函数由现有四个参数改为五个参数：

```go
func NewService(
    maxConcurrent int,
    maxFileSize int64,
    maxSourcePixels int64,
    poolEnabled bool,
    st *stats.Stats,
) *Service {
    return &Service{
        sem:             make(chan struct{}, maxConcurrent),
        maxFileSize:     maxFileSize,
        maxSourcePixels: maxSourcePixels,
        poolEnabled:     poolEnabled,
        st:              st,
    }
}
```

然后把临时常量替换为 Service 字段：

```go
sourceCfg, _, err := InspectSource(imgData, s.maxSourcePixels)
```

Router 的实际创建位置在 `internal/server/http.go`，调用修改为：

```go
svc := process.NewService(
    cfg.Process.MaxConcurrent,
    cfg.Process.MaxFileSize,
    cfg.Process.MaxSourcePixels,
    cfg.Pool.Enabled,
    st,
)
```

构造函数签名变了，已有测试中的调用也必须更新。比如：

```go
// 原调用：NewService(2, 10<<20, pooled, st)
svc := NewService(2, 10<<20, 20_000_000, pooled, st)
```

使用 `rg -n 'NewService\(' internal cmd` 找齐调用位置，避免只修 Router 后被测试里的旧调用挡住。配置测试中的合法 YAML 样例也要加入 `max_source_pixels`；同时补缺失、0、负数的非法配置场景。

### 9.5 最后接 HTTP 映射

在 `internal/process/handler.go` 现有 `switch` 中增加一个分支，保留其他错误处理：

```go
case errors.Is(err, ErrSourcePixels):
    writeJSONError(w, http.StatusRequestEntityTooLarge,
        "source image pixel limit exceeded")
```

进入这个 switch 之前已经调用了 `st.RecordError()`，因此这个分支不用再重复记录一次。这样一次超限请求仍计为一个错误。

走到这里，配置链就完整了：

```text
max_source_pixels: 20000000
→ rawConfig.Process.MaxSourcePixels
→ convert
→ cfg.Process.MaxSourcePixels
→ NewService 第三个参数
→ s.maxSourcePixels
→ InspectSource 的预算判断
→ ErrSourcePixels
→ Handler 返回 413
```

请按这条线讲一次，说明每个值从哪里来、用在哪里。这比只说“我给服务加了个限制”更能证明你理解了实现。

## 10. 用能跑的例子验证理解

### 10.1 先做一个很小的 DecodeConfig 实验

在项目根目录中新建 `.bin/ch01-demo/main.go`，把下面的独立程序放进去。它不调用服务，目的是观察编码字节、配置和 Reader 位置；使用 `40×30`，避免为了研究接口先申请几十 MiB 的图片。

```go
package main

import (
    "bytes"
    "fmt"
    "image"
    "image/png"
    "log"
)

func main() {
    source := image.NewRGBA(image.Rect(0, 0, 40, 30))
    var encoded bytes.Buffer
    if err := png.Encode(&encoded, source); err != nil {
        log.Fatal(err)
    }
    data := encoded.Bytes()

    reader := bytes.NewReader(data)
    cfg, format, err := image.DecodeConfig(reader)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Printf("file=%d bytes, format=%s, width=%d, height=%d\n",
        len(data), format, cfg.Width, cfg.Height)

    _, _, reusedErr := image.Decode(reader)
    fmt.Printf("decode with consumed reader: %v\n", reusedErr)

    decoded, actual, err := image.Decode(bytes.NewReader(data))
    if err != nil {
        log.Fatal(err)
    }
    fmt.Printf("decode with new reader: format=%s, bounds=%v\n",
        actual, decoded.Bounds())
}
```

从项目根目录执行 `go run ./.bin/ch01-demo`。本机 Go 1.25.4 的验证输出为：

```text
file=115 bytes, format=png, width=40, height=30
decode with consumed reader: image: unknown format
decode with new reader: format=png, bounds=(0,0)-(40,30)
```

实际字节数可能随编码实现变化，验证时不要只盯着 115。应该确认配置宽高正确、复用已消费的 Reader 会失败、新 Reader 可以解码。这里的 PNG 像素没有填入复杂图案，文件很容易压缩；它帮助你观察“像素数量”和“文件字节数量”并不是同一个值。

### 10.3 函数测试还不能代替接入测试

函数会拒绝超限，不代表 Service 已经正确调用它。你需要再用预算 1199 调用 Service.Resize 处理这张 `40×30` 图，确认返回的类别是源像素超限；把同一个 Service 的预算设为 1200 后，下一次合法处理应能成功，从而检查早退没有泄漏并发名额。池开和池关各验证一次。

然后通过现有 `resizeImageRequest` 测试助手构造一次上传，让 Handler 处理，确认状态码为 413、响应消息正确、错误计数只增加一次。预算 1200 时应成功返回图片，重新解码输出确认宽高，没有因为 Reader 被消费而失败。声明 PNG 却上传 JPEG 的规则留到第二章，不在这里改变。

要进一步确认“拒绝发生在完整解码前”，可以使用一个只有 PNG 签名和合法 IHDR 的小型测试数据：头部声明超预算宽高，但没有后续像素块。对新实现，应先得到 `ErrSourcePixels`；对于头部尺寸在预算内的同类不完整图片，预检可能成功，完整解码则会得到 `ErrDecode`。前者验证检查顺序，后者验证预检没有取代完整验证。无需制造并完整解码一张巨图来测试保护是否生效。

## 11. 两道结合实际代码的面试追问

### 问题一：图片文件只有 2 MiB，你的服务为什么会接近 1 GiB 内存？

先别背“压缩炸弹”这个词。假设多张图片有很多像素但内容简单，压缩后都不大。你应该从当前源码列出同时存在的对象：Handler 解析得到的表单数据、Service 的输入缓冲、解码后的原图、`NewRGBA` 的目标图，以及编码输出。

然后把并发数量乘进去。你现在的 Service 名额为 4，就可能有四条处理链同时持有这些对象；等待 Service 的请求也可能已经完成 multipart 解析。定位时需要看实际输入像素分布、并发/等待数量和 heap/RSS，不能只看上传字节，也不能把上一节的 RGBA 估算当成测量结果。

你可以先自己讲一遍，再对照下面这段组织方式：

> 文件上限约束的是压缩数据。完整解码后的像素数据、目标图和编码缓冲可能更大，并发会同时持有多份；所以我在 Decode 前检查源尺寸和像素预算，同时保留文件限读。之后还需要目标分配和入口等待限制，并用实际内存数据评估配置。

### 问题二：用户说“上传这张图很卡”，你怎样判断是上传慢还是解码慢？

把这个问题接回第 1 节的流程。如果从客户端开始上传，到服务完整解析表单之间很久，但后面的处理很快，就先查上传链路与表单读取。如果上传已经结束，处理阶段才明显变慢，再比较等待名额、解码、缩放和编码。

你当前只有整段访问日志，不能仅凭一个总耗时断言“肯定是解码”。第一步可以用同一张图片记录 multipart 完成、取得名额、Decode 开始和结束的时间，再比较小图与大图。若大量请求都在等名额，即使单张解码耗时正常，用户仍然会觉得卡。

本章的预检能让超预算图片更早失败，减少后续不合适的完整解码；对预算内图片，它仍然需要解码、缩放、编码，不能宣称加入预检就让所有成功请求变快。分阶段耗时的正式实现放到后续单独一章。

## 12. 本章完成后，重新讲一次流程

现在这条处理线应该变成：先限读文件得到 `imgData`，再用 DecodeConfig 获取源配置；检查正尺寸及像素预算，通过后用新 Reader 完整 Decode；确认解码尺寸，然后沿用原有缩放和编码。源超限返回 Service 错误，Handler 映射为 413；失败时由已经登记的 defer 释放名额和缓冲。

这一章完成的是“源图进入完整解码前的预算检查”。目标图仍需另查：例如原图 `1×10000` 的源像素很少，但把宽度放大到 4096，等比高度会变得非常大。因此源预算通过不代表目标分配安全；下一章会在 NewRGBA 之前限制目标尺寸和像素，并定义真实格式与输出格式规则。这里先说明相邻功能的关系，不提前展开下一章的实现。
