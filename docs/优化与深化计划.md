## 1. 已确定的要求

1. **持续管理版本并定期推送 GitHub**：以小功能阶段组织提交，保存跨天进度，通过开发分支、PR 和阶段标签保留可追溯记录。
2. **实现 Docker 启动和 MySQL 运行**：提供 Dockerfile、Docker Compose、数据库迁移、持久化卷和启动说明，能够从干净环境启动完整服务。
3. **接入 Redis 并验证缓存效果**：复用相同图片与处理参数对应的结果，减少重复解码、缩放、编码及数据库查询；明确失效、容量、并发和故障处理。

上述三项都属于必做范围。本文将实施拆成阶段，Redis 接入不是仅供选择的扩展。

### 1.1 当前优先级：先完成可投递版本

2026-10-11 用户明确要求先完成可投递、能够解释设计并接受深入追问的版本。当前执行顺序改为 R0–R5；M0–M6 保留为完整路线的能力清单，超出首版范围的部分后续再做。

首版运行边界：一个 Go 服务实例，进程内固定数量的 worker；MySQL 保存任务与结果索引；持久化目录保存图片；Redis 缓存结果索引；Docker Compose 启动完整环境。支持单实例停止后重启恢复，不声称已经支持多实例滚动部署或分布式执行。

| R2 Docker 与 MySQL | Dockerfile、Compose、MySQL/Redis 可启动、数据库迁移、连接配置、持久化卷、健康与就绪检查 | 从干净环境启动；容器重新创建后数据库和文件仍可用 |

| R5 投递证据与发布 | 固定样本的冷/热/不命中对照、小图内存基线、一次有依据的主要改进、CI、完整演示与设计说明 | 同条件性能报告、故障演示、GitHub 提交与发布记录、独立讲解记录 |

首版保留同步 `/resize`；异步流程采用 `POST /jobs`、`GET /jobs/{id}` 和按规格下载的接口，一次请求最多支持少量明确规格，具体上限在 R3 开始时固定。暂时保持 JPEG/PNG 等比缩放及简单格式/质量参数。

首版性能工作放在完整业务流程之后开展。当前固定大缓冲区的资源问题在 R1 核对，必要时先采用按需读取；是否重做分级池由基线数据决定。缓存与内存优化分别测量，不能把缓存命中收益记成缩放算法或内存池收益。

**后续范围**：多实例执行与分布式锁、复杂租约续期、独立消息队列、对象存储、多种图片算法、账户/管理后台，以及覆盖全部格式/硬件的大规模压测。这些不会阻塞首版；涉及首版正确性的重复执行、状态恢复、资源上限和缓存降级仍必须验证。

### 1.2 可投递与面试准备的完成标准

每个核心设计都要能连接需求、实现、证据和限制。README、性能报告、设计说明与简历描述保持一致；工具堆叠或测试通过不能代替个人理解。

| 面试追问 | 必须能解释并展示的证据 |
|---|---|
| 一次请求怎样经过系统？ | 同步与异步的调用链，上传、数据库、worker、结果文件和缓存各自的职责 |
| 为什么有文件限制还要限制像素？并发 4 是限制什么？ | 输入压缩大小与解码内存的差异；上传、计算、等待容量各自的限制位置 |
| context 超时会立即停掉计算吗？ | 取消检查发生在哪些位置；排队可取消，普通 CPU 调用的中断限制；实际观察 |
| 两个 worker 能否处理同一任务？进程崩溃怎么办？ | 原子领取、状态流转、有限重试、单实例恢复、幂等结果写入，以及尚未支持的场景 |
| MySQL 记录和图片文件怎样保持一致？ | 文件发布顺序、提交成功条件、部分失败的补偿与清理；不存在跨文件系统与 SQL 的天然原子事务 |
| Redis 挂了、过期了、命中了不存在的文件怎么办？ | 有界回退、持久化结果查询、索引失效处理和故障恢复演示 |
| 怎样证明缓存和内存优化有效？ | 固定输入、并发与版本；冷热缓存分别测量；计算次数、延迟、失败率和内存数据 |

发布前进行一次围绕实际源码与故障场景的复盘。个人理解状态须依据用户实际解释登记，不能由助手替用户勾选“已掌握”。

## 2. 项目定位与当前基线

### 2.1 目标场景

面向博客、电商或内容平台，接收 JPEG/PNG 原图，生成指定尺寸的图片；进一步支持一次提交多个规格、异步处理、状态查询和结果下载。

需要能够解释：

- 如何限制上传、排队和图片计算的资源消耗。
- 内存池是否有效，以及适用的图片大小和并发范围。
- 任务怎样持久化、领取、重试，以及在服务重启后恢复。
- 缓存怎样避免重复计算，以及故障时怎样继续提供服务。
- 如何用同一组实验验证优化结果。

## 3. GitHub 与版本管理规则

### 3.1 分支和提交

- GitHub 稳定分支使用实际存在的 `main`；本地旧 `master` 及其提交历史保留，不重命名或覆盖。
- 2026-10-11 核验发现本地 `master` 与 GitHub `main` 源码树相同，但提交历史不同。首版开发分支基于远端 `main` 创建，避免把两套历史混入 PR。
- 每个阶段创建一个职责明确的开发分支，默认使用 `codex/` 前缀，例如 `codex/upload-limits`、`codex/mysql-jobs`、`codex/redis-cache`。
- 提交以一个可解释的功能或修复为单位，采用 `feat:`、`fix:`、`perf:`、`test:`、`docs:`、`chore:` 等前缀。
- 只暂存当前任务相关文件。现有未提交修改要先检查归属，不能直接全部打包提交。
- 不使用强制推送覆盖历史；保留用户已有修改和其他阶段的工作。

### 3.2 定期推送的具体节奏

| 时机 | 要做的事 |
|---|---|
| 一个小功能完成并通过相关检查 | 当天提交，并推送对应 GitHub 开发分支 |
| 一个阶段跨越多个工作日 | 每个实际开发日结束时，在开发分支保存并推送可解释的进度；未完成部分标明 WIP 和已知问题 |
| 每个阶段验收完成 | 创建或更新 PR，说明行为变化、验证证据和限制；达到检查要求后合并稳定分支 |
| 每周有实际开发活动 | 更新本文的进度表，记录完成项、问题、下一步和 GitHub 链接 |
| 达到发布里程碑 | 创建对应版本标签并推送，发布说明与代码使用同一个版本 |

这是跟随开发进度执行的规则。若需要无人值守的定时推送，后续单独设计；当前不创建定时任务。

### 3.3 检查与版本标签

- 文档提交：检查内容、链接、格式及变更范围。
- Go 行为修改：运行受影响场景的验证、`go test ./...` 与 `go build ./cmd/server`；并发修改补充 race 检查。
- 数据库、Redis、Docker 修改：补充真实依赖的集成验证，并记录启动、故障、恢复结果。
- 性能修改：保留相同环境、输入和负载的优化前后对照，不能只凭代码推断收益。
- 在 GitHub Actions 中逐步加入构建、测试和必要集成检查，稳定分支只合并已验收的版本。
- 采用 `v0.x.y` 记录开发里程碑；补丁修复递增补丁号。`v1.0.0` 仅在完整流程、接口契约和部署验收达到要求后发布。
- 表中的版本号是建议目标，不表示当前已存在这些标签；打标签前检查已有版本，避免覆盖。

### 3.4 仓库内容

提交源码、迁移脚本、示例配置、Compose、文档、测试和压测脚本。通过 `.gitignore` 排除真实凭据、`.env`、上传/输出图片、数据库数据、构建产物及原始性能采样文件；演示素材单独提供小型可分发样例。使用 `.env.example` 说明配置项。

### M4：MySQL 持久化异步批量任务（建议 v0.5.0）

- [ ] 保留同步 `/resize`，新增任务提交、查询和按规格下载结果的流程。
- [ ] 一次提交支持多个明确的缩略图规格，先限定尺寸、格式和质量参数的有效范围。
- [ ] MySQL 保存任务、规格、状态、重试次数、领取者、领取有效期、失败原因和结果元数据；图片字节保存到持久化目录。
- [ ] 状态流转为 `pending -> processing -> succeeded/failed`；每个规格分别保留执行结果。
- [ ] 固定数量的 worker 从持久化任务中领取工作，使用事务和条件更新处理并发领取，设置必要索引。
- [ ] 设置领取有效期及续期/过期恢复机制，旧 worker 不得覆盖新领取者的结果。
- [ ] 区分可重试错误与确定性输入错误，设置重试上限与退避时间。
- [ ] 结果先写临时文件，再完成发布；统一结果标识，重复执行的结果写入可控。
- [ ] 定义任务提交成功的持久化条件，并处理图片文件与数据库记录部分成功时的补偿清理。
- [ ] 验证服务退出、worker 中断、重复领取和重试后的实际行为。

**完成标准**：提交得到任务 ID，查询能看到真实状态，成功结果可下载；服务重启后已接受任务可恢复；重复执行不会错误覆盖或无限生成重复文件。

### M5：Redis 结果缓存与重复计算控制（建议 v0.6.0）

Redis 的核心职责是减少重复工作。MySQL 是任务状态与结果元数据的持久化来源，持久化目录保存图片内容，Redis 内容可以丢失并重建。

#### 缓存对象和键

- [ ] 首先缓存可复用结果的索引与小型元数据：结果 ID、存储位置、尺寸、格式、大小与处理版本。
- [ ] 首版图片结果保存在持久化目录；是否额外缓存小结果字节，根据网络、磁盘和内存测量另行决定，并设置对象大小上限。
- [ ] 原图内容使用 SHA-256 标识；相同内容与参数才复用，不能只用文件名或客户端声明的类型作为键。
- [ ] 处理参数统一规范化，缓存键包含原图哈希、尺寸规则、输出格式、质量及处理版本。
- [ ] 增加处理版本用于算法或默认参数变化后的失效；两个不同规格不得误命中同一结果。

#### 命中、失效与容量

- [ ] 命中时确认结果文件仍存在且元数据有效，然后直接复用，跳过重复解码、缩放和编码。
- [ ] Redis 未命中时先查询持久化结果索引；已有结果则补缓存，确实没有结果才进入计算。
- [ ] 仅在结果发布和元数据提交成功后写缓存；缓存写失败不回滚已经完成的任务。
- [ ] TTL 可配置并加入抖动；明确结果文件保留期限、清理规则与过期索引的处理。
- [ ] 对不可用结果删除缓存索引，防止反复命中已丢失的文件。
- [ ] 配置 Redis `maxmemory` 和明确的淘汰策略，例如先评估 `allkeys-lru`；容器内存预算还需覆盖额外开销。
- [ ] 对确定性无效输入可采用短期失败缓存；数据库断连、超时等暂时错误不得长期缓存为输入失败。

#### 并发与降级

- [ ] 单进程内合并相同键的并发工作；等待请求取消时不会错误取消其他仍需结果的请求。
- [ ] 多 worker 场景结合持久化结果唯一约束、执行领取机制和必要的 Redis 协调，降低同一结果的并发重复计算。
- [ ] 如使用 Redis 锁，必须有唯一持有标识、过期时间、重新检查结果和仅持有者释放的规则；锁不能代替数据库幂等与正确性约束。
- [ ] 缓存读取设置较短超时；Redis 故障时回退持久化查询与受限计算，记录降级状态，避免大量连接重试。

#### 缓存验收

- [ ] 顺序重复请求复用已有结果，新增解码/缩放/编码次数符合预期。
- [ ] 相同图片、不同规格不会错误复用；改变处理版本后旧结果不会误命中。
- [ ] 并发相同请求下统计实际计算次数，验证合并与幂等行为。
- [ ] TTL 到期、缓存清空、结果文件删除时能够恢复；重启 Redis 不丢失任务数据。
- [ ] Redis 停止与恢复后，服务保持可说明的降级行为；计算并发和排队上限继续生效。
- [ ] 分别比较冷缓存、热缓存、混合命中和全不命中负载，记录命中率、结果复用次数、计算次数、数据库查询量、延迟、CPU 和 Redis 内存。

**完成标准**：Redis 已实际接入处理链路；重复计算减少有计数和对照实验支撑；全不命中时的额外开销也被记录，不能只报告热缓存速度。
