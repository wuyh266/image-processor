### 1.2 每次回顾都检查四件事

1. **数据**：输入从哪里来，经过哪些转换，结果归谁持有、保存在哪里？
2. **资源**：内存、计算名额、等待位置、文件和连接何时取得，何时释放？
3. **错误**：失败在哪一层发生，怎样向上返回，HTTP 或任务状态怎样表达？
4. **生命周期**：请求取消、处理超时、进程退出时，哪些工作会停，哪些可能继续？

## 2. 当前真实起点

2026-10-13 读取实际代码：使用标准库 `net/http`，尚未接入 Gin、Docker、MySQL、Redis 或持久化异步任务。源码核验起点为开发分支 `codex/upload-limits` 的提交 `5772f3a`。

### 2.1 启动与请求流程

启动链路：

```text
main → 读取 YAML 配置 → 创建共享 Stats → 创建 Router 和 Service
     → 配置 http.Server → 开始监听 → 等待退出信号 → 取消与 Shutdown
```

一次当前成功的 `/resize` 请求：

```text
访问日志 → Handler 记录请求 → 检查 POST
→ 检查已知请求长度，并限制请求体实际读取
→ 解析 multipart → 取 file → 检查声明格式与 width
→ 创建处理 context → 调用 Service.Resize
→ 等待计算名额 → 限读图片文件 → 完整解码
→ 读取源尺寸 → 计算目标高度 → 创建目标图 → 缩放 → 编码
→ 释放计算名额/归还输入缓冲区 → Handler 返回图片
```

### 2.2 已有能力与实际缺口

| 内容 | 当前事实 | 对后续学习的影响 |
|---|---|---|
| 请求体/文件 | 示例限制请求体 11 MiB、单文件 10 MiB；R1-1 已有技术验证与推送记录 | 下一步关注解码后的像素资源 |
| 图片处理 | JPEG/PNG，等比缩放；Handler 根据上传声明选择输出格式 | 需要区分声明格式、真实格式与输出格式 |
| 图片尺寸 | 完整 `image.Decode` 后才读取尺寸；没有源/目标像素预算 | 先完成 S01、S02 |
| 并发 | `sem` 默认容量 4，覆盖 Service 的读取、解码、缩放、编码 | 尚未完整约束 multipart 解析和等待数量 |
| context | 处理超时从表单解析后开始；目前主要在等待名额时观察取消 | S04 明确阶段检查与退出契约 |
| 日志/统计 | 日志有整段 Handler 耗时；Stats 主要计数 `/resize`，池统计未接入 | 尚不能凭总耗时定位慢在哪一步 |
| 缓冲池 | 池化读取按最大文件上限借用缓冲区，未测量性能收益 | P01 才做有依据的优化 |
| 持久化 | 当前结果保存在内存并随响应返回 | E02、A01–A03 建立数据库与文件的持久化流程 |

R1-1 的测试和构建证据来自 2026-10-12 的实施记录；本次只编写学习文档，不表示重新执行了业务验证。用户审阅验收状态仍以实际反馈为准。

## 3. 为什么按这个顺序构建

先限制单次请求和进程资源，再观察耗时，才能安全地接入持久化和后台工作。MySQL 负责可靠保存任务与结果索引，图片放在持久化目录；随后 Redis 复用已完成结果。完整链路稳定后，再测量缓存和内存方案，最后整理交付证据。

| 顺序 | 学习单元 | 对应阶段 | 前置条件 | 实现后的新增能力 |
|---|---|---|---|---|
| 1 | S01 源图像素预检 | R1-2 | 回顾现有 Resize | 在完整解码前拒绝超预算源图 |
| 2 | S02 输出尺寸与格式规则 | R1-2 | S01 验收 | 目标分配受限，输入/输出格式规则明确 |
| 3 | S03 并发、等待与入口容量 | R1 | S01、S02 验收 | 请求多时，等待与计算资源仍有上限 |
| 4 | S04 取消、超时与退出 | R1 | S03 验收 | 能说明并验证取消和退出能力 |
| 5 | S05 分阶段耗时与统计 | R1、R5 的准备 | 同步链路行为稳定 | 可以区分上传、等待、计算和响应的耗时 |
| 6 | E01 Docker 与依赖运行 | R2 | 同步服务验收 | 容器内服务、MySQL、Redis 可启动 |

| 11 | C01 Redis 结果复用 | R4 | 持久化结果验收 | 同内容、同参数复用已经完成的结果 |

## 4. 同步服务：从当前流程补齐正确性

### S01：源图像素预检——当前下一步

**实现前先过一遍当前流程：** 重点读 `internal/process/service.go` 的文件读取、`image.Decode`、`Bounds`，再读 `handler.go` 如何将 Service 错误变成 HTTP 响应。讲清 `imgData`、解码后的图片、输出缓冲区分别是什么。

**需求与设计：** 文件字节上限不能代替像素上限。先确定源图预算、恰好达到上限是否允许、头部损坏怎样处理，以及检查应属于哪一层。练习时暂用 2000 万像素：`4000 × 3000` 允许，`6000 × 4000` 拒绝；正式值结合并发和内存预算评估。

**你分步实现：**

1. 先用文字解释检查位置与错误返回方式。
2. 学习取得图片配置的接口，完成合法图片的预检路径，再接入超限拒绝。
3. 完善配置传递、错误分类和 Handler 映射；审查尺寸运算中的整数溢出。

`image.DecodeConfig` 可在完整解码前获取尺寸和格式。预检之后如何让完整解码从正确的位置读取，由你设计。参考 [Go 图片配置接口](https://pkg.go.dev/image#DecodeConfig)。

**验证与交付：** 普通 JPEG/PNG、预算之内/恰好/超过、坏头部、池开/关；证明超预算时在完整解码前返回。验收说明区分“像素预算已落实”和“所有图片处理内存已有严格上限”。

**扩展题：文件只有几 MiB，为什么仍可能让服务内存明显增长？** 思考线索：压缩数据、解码像素、目标图、编码输出、并发数量。

### S02：输出尺寸与格式规则

**实现前先过一遍当前流程：** 回顾 S01 实际实现，再跟踪 `targetWidth → newH → image.NewRGBA → 编码 → Content-Type`。同时追踪上传声明如何进入 `detectFormat` 和 Service 的 `format` 参数。

**需求与设计：** 分别定义源预算与目标预算，决定缩放后的取整规则。明确上传声明、真实输入格式和输出格式的关系：例如“声明 PNG、内容 JPEG”是拒绝还是允许转换，必须先定契约。保留首版 JPEG/PNG 范围。

**你分步实现：**

1. 先补目标尺寸与目标像素检查，保证在目标图分配之前生效，避免高度计算溢出。
2. 再实现已经确定的格式规则，保证成功响应的 Content-Type 与实际编码一致。
3. 检查直接调用 Service 时是否也能遵守关键资源约束。

**验证与交付：** 极端长宽比、目标像素边界、声明与内容不一致、损坏内容、实际输出格式和尺寸。保留一张格式行为表，作为接口契约。

### S03：计算并发、等待容量与上传入口

**实现前先过一遍当前流程：** 从 multipart 解析到 Service 的 `sem` 获取和释放逐步走一遍。指出哪些步骤已经消耗资源但还未取得名额，哪些请求正在等待，文件和缓冲区在什么时候仍被持有。

**需求与设计：** 把上传解析中的请求、等待计算的请求、正在计算的请求分开考虑。明确各自容量、等待时限、满时响应，以及拒绝发生在什么位置；用“同时最多多少个、每个可能占多少内存”解释配置。

**你分步实现：**

1. 先设计容量表与名额的取得/释放规则，确定排队满时的 HTTP 行为。
2. 实现有界的计算等待，再落实上传解析的入口限制。
3. 检查所有失败和取消路径，保证不泄漏名额；补运行数、等待数和拒绝计数。

**验证与交付：** 并发超过容量、等待超时、等待期间取消、坏文件失败后名额可复用；容量满时快速得到约定响应。说明入口限制覆盖的是哪些请求，进程内限制无法直接约束所有客户端连接。

**扩展题 1：这个架构如果突然流量变大，你会怎样处理？** 先基于当前单实例回答：到达速率、完成速率、排队增长、资源瓶颈、限流/拒绝和容量预算。再讨论扩容需要先补哪些持久化与协调能力。

**扩展题 2：把 `max_concurrent` 从 4 改成 100，吞吐一定会上升吗？** 思考线索：CPU、单图内存、GC、等待时间与 P95、失败率，用什么实验判断。

### S04：context、处理超时与优雅退出

**实现前先过一遍当前流程：** 从 `r.Context()` 到处理 context，再到 Service 的 `select`；另走一次 `main` 的退出信号、`serverCancel` 和 `Shutdown`。指出当前超时从哪里开始，读取、解码、缩放、编码各自是否观察取消。

**需求与设计：** 区分上传时限、排队时限和处理时限。定义阶段之间的取消检查以及退出时对新请求、等待请求、处理中请求的策略。不能仅凭传入 context 就承诺普通 CPU 函数立即中断。

**你分步实现：**

1. 写下各阶段取消能力和预期错误，再实现阶段边界检查。
2. 明确信号与退出顺序；为后续 Linux 容器补齐适用的终止信号处理。
3. 验证退出等待预算，说明预算到期后仍未结束的工作怎样处理。

**验证与交付：** 已取消 context、等待名额时取消、阶段之间取消、退出期间新请求与在途请求的行为。预期结果必须符合真实观察能力，不把超时测试写成无法保证的即时终止。

**扩展题：客户端超时了，为什么服务端仍可能在计算？** 从取消信号是否到达、代码何时检查、正在调用的函数能否中断三个层次解释。

### S05：分阶段耗时与可解释统计

**实现前先过一遍当前流程：** 阅读 `internal/server/logging.go` 和 `internal/stats/stats.go`，回顾一次请求的全部阶段。当前访问日志测量整段 Handler，不能直接告诉你具体慢在哪里；成功计数发生在响应写出前，也不等于客户端已收到结果。

**需求与设计：** 先用一个请求关联标识串联日志，记录上传解析、等待、读取、预检、解码、缩放、编码和响应写出的耗时。定义计算次数、运行/等待数量、拒绝/失败计数。后续接依赖时逐步增加数据库、文件和缓存耗时。

**你分步实现：**

1. 先为一条请求记录阶段耗时，约定起止位置与含义。
2. 再接入必要的并发安全计数，明确计算成功与响应写失败的口径。
3. 用小图、大图、等待中的请求做一次对比，解释耗时差异。

**验证与交付：** 日志能串联同一请求，错误路径也有结束记录，阶段边界一致，计数不会因并发而丢更新。无需在这一课先搭完整监控平台。

**扩展题 1：用户说“很卡”，你从哪些角度排查？** 先问发生在哪一步、什么样的图片、何时开始、是否只影响部分请求，再按客户端/网络、入口与上传、排队、计算、依赖与磁盘逐层找证据。第 8 节提供练习表。

**扩展题 2：平均耗时很好，但部分用户很慢，怎样解释？** 思考线索：输入分布、P95/P99、慢请求样本、排队与依赖波动；平均值能隐藏哪些问题。

### E02：MySQL 连接、迁移与任务数据模型

**实现前先过一遍当前流程：** 回顾 E01 的启动与依赖就绪，再追踪目前配置如何进入 Router/Service、同步图片结果怎样返回。指出任务数据与图片文件分别需要放在哪里，以及为什么现有内存结果无法用于重启恢复。

**需求与设计：** MySQL 保存任务、规格、状态与结果元数据；图片内容保存在持久化目录。先设计字段、主键、唯一约束、查询方式和索引，再设计连接池、查询时限、迁移执行和数据库就绪检查。

**你分步实现：**

1. 先用业务例子画出任务、规格和结果的关系，写第一份版本化迁移。
2. 接入真实数据库连接，完成一条写入与一条读取，使用能传递 context 的数据库调用。
3. 定义存活与就绪区别，完成连接配置和迁移失败时的行为；测试容器重建后记录仍可查询。

数据库调用也需要把 context 传到支持它的接口，不能只创建一个超时值。参考 [Go 数据库操作取消](https://go.dev/doc/database/cancel-operations)。

**验证与交付：** 新库迁移、已有库升级、重复启动不重复执行已完成迁移、读写查询、超时/断连与重连、持久化。事务与连接的释放时机要能讲清。

**扩展题 1：用户变多后，数据库连接数应该无限加大吗？** 思考线索：连接池等待、SQL/事务耗时、数据库承载能力、索引与锁竞争。

**扩展题 2：任务查询越来越慢，怎样判断是索引问题还是连接池等待？** 先明确慢的是获取连接还是执行 SQL，再寻找执行计划、扫描量、连接池统计与锁等待的证据。

## 6. 异步任务：把 HTTP 请求和计算生命周期分开

### A01：任务提交、状态查询与结果下载接口

**实现前先过一遍当前流程：** 回顾已经稳定的同步请求链路与 E02 数据访问。解释同步请求为何必须等计算完成，以及异步提交成功时至少需要保存哪些数据。

**需求与设计：** 保留 `/resize`，逐步增加 `POST /jobs`、`GET /jobs/{id}` 和按规格下载的接口。先支持一个规格，验收后再支持有数量上限的多个规格；扩展时定义各规格状态与总任务状态的汇总规则，明确部分成功怎样表达。接受任务后，浏览器断开不应自动撤销持久化任务。

**你分步实现：**

1. 先明确任务提交的持久化成功条件，完成原图保存和 `pending` 任务记录；处理文件与记录部分失败的清理。
2. 实现查询：不存在、等待、处理中、成功和失败各怎样返回。本小步没有 worker 时，任务可以停在 pending，不能伪造完成状态。
3. 定义成功结果下载契约；与 A02 执行结果联调后验收完整路径。

**验证与交付：** 合法提交取得可查询 ID；非法规格、未完成任务下载、任务不存在、数据库或文件写失败；客户端中断后确认已经接受的任务仍在。异步提交也要有容量预算，持久化队列不能无限增长。

**框架安排：** 本课开始时根据实际路由复杂度决定是否引入 Gin。若引入，先回顾 `net/http` 的路由、Handler 和中间件，只完成已有接口等价迁移并验证，再新增任务接口；Service 和数据访问职责保持清楚。这不是首版必须堆入的依赖。

### A02：固定 worker 与原子领取

**实现前先过一遍当前流程：** 从 A01 的上传、持久化、pending、查询走一遍，列出尚无人执行的工作。回顾 Service 的计算名额、context 和图片资源限制，确认 worker 调用时仍遵守这些约束。

**需求与设计：** worker 数量固定。定义谁能把任务从 pending 改成 processing，两个 worker 同时发现同一任务时怎样保证只有一个领取成功；设计领取者或执行标识、事务边界和条件更新。

**你分步实现：**

1. 先实现一个 worker 的成功路径，完成状态流转和结果保存。
2. 再实现原子领取与多 worker，领取事务结束后才进行耗时图片计算。
3. 明确 worker 自身的生命周期、轮询/唤醒方式，以及与 Service 并发预算的关系。

事务锁定读取是可以评估的领取机制之一；MySQL 的 `SKIP LOCKED` 可跳过已锁定行，适合部分队列式访问，选择前仍需理解其语义和实际索引。参考 [MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

**验证与交付：** 多 worker 同时领取、处理成功/失败后的状态、实际执行计数、无任务时不忙循环、停止时不再领取。说明“领取不重复”与“失败恢复后可能重新执行”的区别。

**扩展题 1：两个 worker 同时看到同一条 pending 任务，为什么先查后改可能不可靠？** 思考线索：并发时序、事务范围、锁、条件更新结果。

**扩展题 2：改成两个服务实例，还能直接使用目前的进程内 channel 吗？** 分别说明每个进程的容量、数据库领取、共享文件位置和任务归属；跨实例能力放到后续扩展。

### A03：有限重试、结果发布与单实例恢复

**实现前先过一遍当前流程：** 从领取到读取原图、计算、写结果文件、写元数据、更新任务状态逐步走一遍。在每两步之间假设进程退出，列出可能留下的状态。

**需求与设计：** 区分永久输入错误与暂时依赖错误，定义最大尝试次数与退避。结果需要临时写入、完整发布和元数据提交的规则；同一工作重新执行时，结果标识、发布和清理应可控。

**你分步实现：**

1. 先实现有上限的重试、下次可执行时间与失败终态，避免领取循环反复立即重试。
2. 再实现结果发布、条件状态更新和补偿清理，防止数据库成功却指向不完整文件。
3. 在确认旧进程已退出的单实例前提下，设计启动时对遗留 processing 的恢复；把恢复后重复执行纳入验证。

首版不把启动恢复机制当成多实例租约机制。日后支持多实例或旧执行仍可能存活时，需要进一步设计有效期、续期、执行标识和旧执行写入保护。

**验证与交付：** 处理中退出并重启、临时故障重试成功、永久错误不反复重试、达到上限失败、文件成功但元数据失败、重复执行与清理。证明已接受任务不会只存在内存队列里。

**扩展题 1：图片文件写成功了，数据库提交失败，能回滚图片吗？** 思考线索：两种存储各自的提交边界、临时文件、补偿、清理和幂等。

**扩展题 2：服务重启后重新执行任务，怎样避免生成一堆重复结果？** 结合稳定结果标识、唯一约束、条件更新和发布规则，解释可提供的保证。

## 7. Redis：复用结果并处理并发与故障

### C01：内容标识、缓存键与结果索引复用

**实现前先过一遍当前流程：** 回顾 A03 的原图、规格、结果文件、MySQL 元数据及计算计数。明确“客户端重复提交”“任务 ID 不同”和“实际上能共用一个结果”之间的关系。

**需求与设计：** Redis 先缓存结果 ID、位置、格式、尺寸等小型索引，图片内容仍在持久化目录，MySQL 仍是持久化元数据来源。键由原图内容哈希、标准化处理参数和处理版本构成。

**你分步实现：**

1. 先定义等价请求与缓存键，用具体例子检查参数默认值和顺序是否规范化。
2. 再接入 Redis 查询、持久化索引回源和结果文件校验，已有结果直接复用。
3. 只有完整结果发布且元数据提交成功后才写缓存；缓存写失败不否定已完成结果。

**验证与交付：** 同内容/同参数复用，不同规格不误命中；Redis 未命中但持久化结果存在时补缓存；缓存命中缺失文件时清除无效索引。报告 Redis 命中、持久化结果复用、真正计算次数三种口径。

### C02：并发重复工作、TTL、容量与降级

**实现前先过一遍当前流程：** 按 Redis 命中、Redis 未命中但 MySQL 命中、两者都没有结果、文件缺失四条路径各走一次。模拟两个调用同时发现结果不存在，找出重复计算发生的位置。

**需求与设计：** 首版在单进程内合并相同键的工作，并保留持久化结果唯一约束。TTL、失效、结果保留期、Redis 容量和淘汰规则需要配套；Redis 断连时使用较短超时，回退持久化查询与受限计算，防止无限等待或重试。

**你分步实现：**

1. 先定义共享计算与各等待者的生命周期，再实现同键并发合并；HTTP 请求 context、后台任务 context 和共享工作 context 的关系必须明确。
2. 再加入 TTL、适度抖动、索引失效和 Redis 容量配置，说明缓存过期与图片文件删除是两件事。
3. 最后落实缓存故障降级，沿用有界计算/等待，同时为数据库回源和任务积压制定容量保护。

可评估 Go 的 [singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight) 合并同进程重复调用；它本身不提供跨进程协调或自动的取消策略。Redis 的 `maxmemory` 和淘汰策略需要按访问模式选择，容器总内存还需预留额外开销。参考 [Redis 缓存容量与淘汰](https://redis.io/docs/latest/develop/reference/eviction/)。

**验证与交付：** 同键并发的实际计算次数、一个等待者取消、TTL 到期、缓存清空、文件删除、Redis 停止与恢复；全不命中负载下，计算、回源与等待仍然受限。暂时依赖失败不能长期当作输入错误缓存。

**扩展题 1：大量相同请求同时遇到缓存过期，会发生什么？** 结合重复回源、重复计算、同进程合并、键失效和容量保护解释，并说明方案作用范围。

**扩展题 2：Redis 挂了，你选择全部报错还是回源？回源会有什么新问题？** 先依据本项目缓存可丢失的定位讨论，再考虑数据库、worker 与等待队列的额外压力。

## 8. 性能排查、交付与面试复盘

### P01：固定实验与有依据的内存优化

**实现前先过一遍当前流程：** 从提交到结果复用/计算/下载走完整链路，回顾阶段耗时和计数。单独检查现有池的借用/归还与约 10 MiB 输入缓冲区，确认哪些配置和统计实际生效。

**需求与设计：** 用固定样本、并发、环境和版本测量吞吐、P50/P95、失败率、实际计算次数、分配、堆内存与 GC。分别比较冷缓存、热缓存、混合命中和全不命中，避免把缓存收益计入缩放或内存池收益。

**你分步实现：**

1. 先跑可复现基线，依据阶段耗时选择要采集的 profile。
2. 根据证据决定一次主要改进；若固定大缓冲区是主要问题，再比较按需读取或有界分档复用。
3. 在同样条件下复测，保留失败或无收益的结果，解释适用范围和取舍。

Go 诊断工具分别提供 CPU、heap、goroutine、block 和 mutex 等观察角度；采样应围绕已经提出的判断。参考 [Go Diagnostics](https://go.dev/doc/diagnostics)。

**验证与交付：** 优化前后行为一致，图片输出正确，数据可复现，资源没有失控增长。性能报告附环境、输入、并发、版本和运行次数；数字来自实际执行。

**扩展题：加了 `sync.Pool` 为什么可能没有更快，还占了更多内存？** 思考线索：对象大小、分配与复制、复用范围、GC、是否测到了主要开销。

### 8.1 “用户觉得卡”的专项练习

先让用户描述“卡”发生在上传、等待任务、查询状态还是下载；取得时间范围、图片大小/像素/格式、任务或请求标识，并用一条样本复现。随后按链路寻找证据，再提出改动。

| 观察角度 | 先问什么 | 在本项目找什么证据 | 可以验证的判断 |
|---|---|---|---|
| 客户端与网络 | 上传慢、首个响应慢，还是下载慢？是否只在某网络发生？ | 客户端阶段时间、请求/响应字节、服务端收到请求的时间 | 网络或传输问题是否解释了总耗时 |
| 入口与上传 | 请求体或图片是否变大？被拒绝还是进入了处理？ | 解析/读取耗时、体积、像素、入口运行数与拒绝数 | 上传路径是否消耗主要资源 |
| 等待与任务积压 | 等待数、队列深度和最老任务年龄是否增长？ | 到达/完成速率、计算运行数、排队耗时 | 工作到达速度是否超过持续处理能力 |
| 图片计算 | 小图也慢，还是大图/某格式慢？ | 解码/缩放/编码耗时、CPU profile、格式与像素分组 | 是否是某阶段 CPU 开销增加 |
| 内存与运行时 | 堆、分配、GC 与 goroutine 数是否一起增长？ | heap/goroutine profile、GC 与进程内存、缓冲区大小 | 是否是大量分配、等待或资源未释放 |
| MySQL（接入后） | 等连接慢、执行 SQL 慢，还是等待锁？ | 连接池等待、查询耗时、执行计划、锁等待 | 连接池、索引或长事务是否是瓶颈 |
| Redis（接入后） | 命中下降、读写超时，还是反复命中失效文件？ | Redis 耗时、命中/淘汰、回源量、真正计算次数 | 缓存异常是否增加了下游压力 |
| 文件与容器（接入后） | 写结果/下载是否变慢？容器资源是否受限？ | 文件读写耗时、磁盘、CPU 限制/内存事件、容器日志 | 存储或运行环境是否解释了延迟 |

练习时每次只选择一条假设，例如“CPU 未满但用户等待很久，怀疑连接池或队列等待”。说明还需要哪项证据，采集后判断成立与否，再提出可验证的调整。表中证据在对应功能实现后逐步获得，当前不是全部已有。
